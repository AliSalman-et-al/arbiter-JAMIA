# Figure legends

## Figure 1. How ARBITER works

**Figure 1. How ARBITER works.** A reviewer defines the outcome and approves the proposed result before domain assessment. Guided by the `/arbiter-assess` skill, the LLM agent reads reports and registry records and submits signalling answers with evidence. The deterministic ARBITER server makes no model calls: it captures and versions sources, validates submissions, binds evidence spans, proposes judgements using the official RoB 2 algorithms, records history and exports a verifiable `.arbiter.zip` bundle. The assessing model can adopt a different domain judgement only through a recorded, reasoned override. Monospace labels name representative MCP tools; italic labels summarize responses. The red return arrow illustrates rejection of invalid or unbound submissions. Across the 102 trials, the server rejected 53 of 637 `save_domain_judgment` calls (32 for evidence or citation structure, 21 for other input errors); nothing is saved from a rejected call and the agent may resubmit. All 47 trial-domain assessments with at least one rejection ended with a successful save; no domain ended without one. All 53 rejections were followed by an accepted save for the same domain, with one domain-less PALOMA-2 call attributed to D1 from the D1 retries immediately before and after it. In AVATAR, one of seven save calls was rejected and then successfully resubmitted. The saved bundle contains source identities and bound evidence, rather than copies of the trial PDFs. MCP, Model Context Protocol.

Alt text: Four phases—Capture, Propose and approve, Assess each domain, Review and export—span Reviewer, lavender LLM agent, mint ARBITER server and pale-yellow Bundle lanes. Human approval through arbiter review unlocks domain work. Tool calls descend from the agent to the server; response summaries return upwards. The server validates and binds evidence, computes proposed judgements, records history and packages the assessment. A continuous red return arrow connects the pill below the server lane, “invalid or unbound answer → not saved”, to the agent lane. The reviewer receives a report and a verifiable bundle.

Answer pills immediately follow their questions. Yellow denotes direct support, lavender denotes context, and an unfilled dashed outline denotes inference. The same highlight colour links evidence to the corresponding words in the recorded reasoning. The plain-text statement about a missing dated analysis plan is an uncertainty claim, not something established by the context quotations alone. Low judgement chips remain plain; pale ARBITER-blue judgement chips and a heavier D5 border identify D5 as the domain driving Overall. The recorded unknown has a bold “Unknown:” label and grey text. Numbered callouts identify **1**, a text span bound to a source page, line range and source-version hash; **2**, RoB 2 branching that switches questions off; **3**, the deterministic server algorithm that computes the proposed judgement; and **4**, an unknown recorded explicitly rather than supplied as an assumed fact. The displayed hash prefixes identify searchable source projections, not PDF byte hashes. Line ranges identify the complete bound span; displayed quotations can be shorter. Ellipses mark omissions, and two extraction line breaks are joined without changing words. ## Figure 3. Benchmark inclusion and adjudication flow

Sixteen meta-analyses supplied 105 trials. Three unsupported-design trials were excluded from every arm and analysis. Four arms each assessed the 102 included trials: ARBITER and Unassisted with Sonnet 5.5 (main analysis), and with Haiku 5.5 (supplement). There are 510 D1–D5 cells per arm and 81 Published Overall labels. Of 154 disputed cells, 129 had consensus and 25 were split. The Sonnet arms differed on 62 consensus cells (54 ARBITER wins, 7 Unassisted, 1 neither) and 18 split cells.

Alt text: A centred flow diagram follows 105 trials through three exclusions to four arms of 102 trials, then 154 disputed cells and the consensus and split branches.

## Figure 6. Individually decisive signalling questions behind consensus losses

Paired bars show individually decisive questions among consensus losses where both independent judgements equal the consensus preferred judgement (10 ARBITER and 47 Unassisted losses). ARBITER appears above Unassisted. Facet labels give eligible losses. A question is decisive if substituting the unanimously agreed independent answer alone changes the official algorithm output. The lighter arm-colour bars (light blue for ARBITER, light orange for Unassisted) count cells without any individually decisive question, including jointly decisive cells. A cell can contribute several question bars: reconciliation is the number of distinct cells contributing at least one question plus cells in the lighter bars, not the sum of question frequencies. Question bars count question occurrences; lighter bars count cells. The no-single-decisive-question row is omitted when both counts are zero (D1). Zero-count labels are omitted. D2 uses effect of assignment.

Alt text: Domain facets compare sources on decisive questions and add lighter blue and orange remainder bars for cells with no individually decisive question. Question 5.1 is the most frequent Unassisted decisive question.
