# Legends and alt text: Figures 1–2

**Figure 1. How ARBITER works.** A reviewer defines the outcome and approves the proposed result before domain assessment. Guided by the `/arbiter-assess` skill, the LLM agent reads reports and registry records and submits signalling answers with evidence. The deterministic ARBITER server makes no model calls: it captures and versions sources, validates submissions, binds evidence spans, proposes judgements using the official RoB 2 algorithms, records history and exports a verifiable `.arbiter.zip` bundle. The assessing model can adopt a different domain judgement only through a recorded, reasoned override. Monospace labels name representative MCP tools; italic labels summarize responses. The red return arrow illustrates rejection of invalid or unbound submissions. Across the 102 trials, the server rejected 53 of 637 `save_domain_judgment` calls (32 for evidence or citation structure, 21 for other input errors); nothing is saved from a rejected call and the agent may resubmit. All 47 trial-domain assessments with at least one rejection ended with a successful save; no domain ended without one. All 53 rejections were followed by an accepted save for the same domain, with one domain-less PALOMA-2 call attributed to D1 from the D1 retries immediately before and after it. In AVATAR, one of seven save calls was rejected and then successfully resubmitted. The saved bundle contains source identities and bound evidence, rather than copies of the trial PDFs. MCP, Model Context Protocol.

Alt text: Four phases—Capture, Propose and approve, Assess each domain, Review and export—span Reviewer, lavender LLM agent, mint ARBITER server and pale-yellow Bundle lanes. Human approval through arbiter review unlocks domain work. Tool calls descend from the agent to the server; response summaries return upwards. The server validates and binds evidence, computes proposed judgements, records history and packages the assessment. A continuous red return arrow connects the pill below the server lane, “invalid or unbound answer → not saved”, to the agent lane. The reviewer receives a report and a verifiable bundle.

**Figure 2. One trial, end to end.** AVATAR, all-cause death, was selected as an illustrative cardiology trial whose D1–D5 judgements are not all Low; it is not presented as a representative case. Each domain row links an archived signalling answer to an excerpt of its bound evidence and recorded justification, explicitly labelled “Justification” to distinguish the agent’s words from quoted source text. Answer pills immediately follow their questions. Yellow denotes direct support, lavender denotes context, and an unfilled dashed outline denotes inference. The same highlight colour links evidence to the corresponding words in the recorded reasoning. The plain-text statement about a missing dated analysis plan is an uncertainty claim, not something established by the context quotations alone. Low judgement chips remain plain; pale ARBITER-blue judgement chips and a heavier D5 border identify D5 as the domain driving Overall. The recorded unknown has a bold “Unknown:” label and grey text. Numbered callouts identify **1**, a text span bound to a source page, line range and source-version hash; **2**, RoB 2 branching that switches questions off; **3**, the deterministic server algorithm that computes the proposed judgement; and **4**, an unknown recorded explicitly rather than supplied as an assumed fact. The displayed hash prefixes identify searchable source projections, not PDF byte hashes. Line ranges identify the complete bound span; displayed quotations can be shorter. Ellipses mark omissions, and two extraction line breaks are joined without changing words. D4 question 4.3 is supported by the bound report sentence stating that data and safety monitoring board members were not blinded; question 4.4 rests on an inference about an outcome involving no judgement. D5 answers NI, PN and PN produce Some concerns, adopted without override. D1–D4 are Low; D5 drives Overall Some concerns under the official RoB 2 overall rule, applied by the server. The archived verifier reports verified, which establishes structural and evidence-binding checks rather than clinical correctness.
